# 위키 확장 — 일반 문서와 `위키` 메뉴 (제안)

> 상태: **0~2단계 구현됨, 4단계 일부 구현됨** (2026-09-06). 아래 "결정된 것" 여섯
> 가지는 확정이고, `단계` 표의 0·1·2단계가 들어갔다. 4단계는 `wiki_links`,
> "아직 없는 문서"에 일반 문서 합치기, `[[분류:…]]`(태그·소속 조회·관문 펼치기 패널·
> 04 나무의 하위분류 중첩)까지 들어갔다 — 역링크 화면(문서→역링크 목록)·관문
> 포스터는 아직이다. 3단계는 아직 제안이다.
> `docs/WIKI_MODEL.md`의 후속이며, 그 문서의 결정을 뒤집지 않고 넓히기만 한다.
> 승인되면 `docs/PRD.md`에 FR을 추가하고, 이 문서가 그 부속 설계가 된다.

지금 위키에는 매치업 문서밖에 없다. 룬·정글 동선·용어 같은 **일반 문서**를 들이고,
그 전부를 한자리에서 찾을 수 있는 `위키` 메뉴를 만든다.

## 결정된 것

| 물음 | 결정 |
| --- | --- |
| 새 문서 생성 | **제목이 겹치면 생성 불가.** 그 밖에는 전부 보류되고 운영자가 승인해야 만들어진다 |
| 일반 문서의 섹션 | **상대법 문서와 같다.** 본문 + 이름 붙은 섹션들, 편집 단위도 그대로 |
| 매치업 문서 | `위키` 메뉴에 함께 담는다. 목록도 최근 변경도 하나다 |
| 주소 | 한글을 쓴다. `/wiki/정글 동선` |
| 분류 만들기 | 본문에 `[[분류:…]]`를 적으면 생긴다. **만드는 권한이 따로 없다** |
| 나무의 최상위 | 운영자가 **관문**으로 고른 서넛. **한 축에서만 고른다.** 그 아래는 편집자에게 열려 있다 |
| 관문이 늘면 | 회전시키지 않는다. 표지에 거는 셋을 운영자가 **편성**하고 나머지는 나무에 이름으로 선다 |

## 이미 준비된 것

새로 지어야 할 것이 생각보다 적다. 확장을 미리 염두에 두고 지은 자리가 남아 있다.

| 있는 것 | 확장에 쓰이는 방식 |
| --- | --- |
| `resolveWikiTitle` | "일반 문서 저장소가 생기면 갈래를 하나 더 둔다"고 주석에 적어 둔 그 자리 |
| `wiki_edits` · `wiki_sections` | 전부 `doc_id` 기준이다. **매치업에 매여 있지 않다** |
| 편집·검토·역사·되돌리기 | 섹션 단위로 돌아가므로 문서 종류를 묻지 않는다 |
| `listRecentChanges` | 이미 있다. 지금은 관리자 전용일 뿐이다 |
| `MergeEditScreen` | 빈 본문에서 시작하면 그대로 "새 문서 쓰기"다 |
| `WikiDocument` | 섹션 목록을 받아 그린다. 섹션이 어디서 왔는지 묻지 않는다 |

매치업에 매여 있는 것은 **주소를 다루는 얇은 층**뿐이다. `submitEdit`이
`champion_slug`로 문서를 찾고, 화면이 `/matchup/<챔피언>` 주소를 짓는다. 이 층만
"문서를 가리키는 법"으로 한 단계 올리면 나머지는 그대로 쓴다.

> **2026-09-04 개정.** 매치업 문서의 식별자가 `(포지션, 챔피언)`에서 `챔피언`으로
> 바뀌었다 (마이그레이션 0003). 포지션은 패치마다 바뀌는 분류라, 그것을 정체성에
> 두면 분류를 고칠 때마다 문서가 생겼다 없어졌다 한다. 아래 설계 중 매치업 문서의
> 식별자를 전제한 부분은 이 개정을 반영해 고쳤다.

## 한 이름 공간에 두 종류

문서를 두 저장소로 쪼개지 않는다. 쪼개면 편집·검토·역사·최근 변경이 전부 두 벌이
되고, "최근 바뀐 문서"를 보려면 두 목록을 번갈아 봐야 한다.

```
wiki_docs
├── kind = 'matchup'   →  champion_slug로 식별.  /matchup/ahri
└── kind = 'article'   →  title_key로 식별.      /wiki/룬
```

### 섹션은 상대법 문서와 같다

일반 문서도 **본문 하나 + 이름 붙은 섹션 여럿**이다. 매치업 문서에서 `공통 상대법` +
`제드로 상대할 때` `야스오로 상대할 때`인 것이, 룬 문서에서는 `본문` +
`정밀` `지배` `마법`이 된다. 목차 하나로 이어지고 번호가 문서 전체를 관통하는 것도,
섹션이 곧 편집 단위이자 즉시반영·검토 판정 단위인 것도 그대로다.

**다른 것은 섹션 이름이 어디서 오는가뿐이다.**

| | 매치업 문서 | 일반 문서 |
| --- | --- | --- |
| 섹션 이름 | 챔피언 카탈로그에서 고른다 (`MeCombobox`) | 편집자가 직접 적는다 |
| 이름 저장 | 안 한다 — 슬러그로 카탈로그를 되찾는다 | `wiki_sections`에 함께 저장해야 한다 |
| 앵커 | `me-<챔피언 슬러그>` | `s-<섹션 키>` |

그래서 `wiki_sections.me_slug`는 이제 **섹션 키**다. 매치업에서는 챔피언 슬러그이고
일반 문서에서는 섹션 이름을 정규화한 값이다. 열 이름은 바꾸지 않는다 —
`wiki_edits.me_slug`가 짝을 이루고 있어 함께 바꾸면 손댈 곳이 넓어진다. 주석으로 뜻을
넓히는 편이 싸다.

### 스키마 변경

```sql
-- wiki_docs에 더한다.
kind        TEXT NOT NULL DEFAULT 'matchup',   -- 'matchup' | 'article'
title       TEXT,                              -- 일반 문서의 표시 이름. 예: '정글 동선'
title_key   TEXT,                              -- 정규화한 이름. 주소이자 유일성의 근거
-- 'published' | 'proposed'. 승인 전 문서는 목록·링크·검색 어디에도 나오지 않는다.
doc_status  TEXT NOT NULL DEFAULT 'published',

-- champion_slug는 마이그레이션 0003에서 이미 NULL 허용이고 유일 인덱스도 붙어 있다.
-- 1단계에서는 표를 다시 만들 필요 없이 아래 열들을 ALTER로 더하기만 하면 된다.
-- 승인 전 제안도 같은 이름을 잡는다. 아래 "제목이 겹치면" 참고.
-- 거절된 제안은 title_key를 비워 이름을 놓아준다. NULL은 서로 다른 값으로 취급된다.
CREATE UNIQUE INDEX idx_docs_article ON wiki_docs (title_key)
  WHERE kind = 'article' AND title_key IS NOT NULL;

-- wiki_sections에 더한다. 일반 문서의 섹션 이름.
-- 매치업 문서는 NULL이다 — 이름을 챔피언 카탈로그가 갖고 있다.
title       TEXT;
```

표를 다시 만드는 작업은 **마이그레이션 0003에서 이미 끝냈다.** 그때 `champion_slug`를
NULL 허용으로 열어 두었으므로 1단계는 `ALTER TABLE ADD COLUMN`만 하면 된다 — 되돌릴
수 없는 작업을 두 번 하지 않으려고 미리 그 모양으로 만들었다.

> **부모 표를 다시 만들 때의 함정.** `wiki_sections`·`wiki_edits`가 `ON DELETE
> CASCADE`로 `wiki_docs`를 참조한다. 외래 키가 켜진 채 부모를 `DROP TABLE`하면
> 암묵적 DELETE가 일어나 **자식이 함께 지워진다.** `PRAGMA defer_foreign_keys`는
> 제약 검사를 미룰 뿐 CASCADE 동작은 막지 못한다(0003을 로컬에 처음 적용했을 때
> 실제로 섹션 6개와 편집 13개가 사라졌다). 0003은 자식을 제약 없는 임시 표에 옮겨
> 두었다가 되돌려 놓는 방식으로 처리한다. 같은 일을 또 할 때 그 파일을 본뜬다.

`doc_id`는 지금 `doc-<포지션>-<챔피언>`이다. **기존 값을 건드리지 않는다** —
`wiki_edits`·`wiki_sections`가 전부 이 값을 참조하고 있다. 일반 문서는
`doc-a-<uuid>`로 짓는다. 이름에서 짓지 않는 것은 거절된 제안이 이름만 놓아주고 행은
남기 때문이다 (아래 "승인되기까지") — 같은 이름이 다시 제안되면 이름에서 지은 id가
부딪힌다.

### 이름이 곧 주소다

`[[정글 동선]]`이라고 쓰면 그 이름으로 문서를 찾는다. 이름과 주소가 따로 놀면
편집자가 둘을 함께 관리해야 하는데, 그건 사람이 지킬 규칙이 아니다.

`title`은 보여줄 이름 그대로 두고, `title_key`는 `wikiLink.ts`의 `normalize()`와
같은 규칙(소문자·공백 제거)으로 만든다. 그래야 `[[정글 동선]]`과 `[[정글동선]]`이
같은 문서에 닿는다. 주소는 `/wiki/정글 동선`을 URL 인코딩한 것이다.

#### 매치업 문서의 이름은 `아리 상대법`이다

챔피언당 문서가 하나이므로 이름에 포지션이 들어가지 않는다. `럭스 상대법`이 가리킬
문서는 언제나 하나뿐이다. 문서 화면의 `<title>`도 같은 값이라, 목록·검색·최근 변경이
전부 한 이름을 쓴다.

주소는 `/matchup/ahri`다. 일반 문서와 달리 이름이 곧 주소는 아니지만 (주소는 슬러그를
쓴다), **이름은 하나다.**

`resolveWikiTitle`은 사람들이 실제로 적을 만한 꼴을 함께 받는다.

| 적은 것 | 결과 |
| --- | --- |
| `[[아리 상대법]]` | 정식 이름 |
| `[[미드 아리 상대법]]` | 포지션을 앞에 붙인 꼴. 포지션은 이제 장식이라 무시한다 |
| `[[미드/아리]]` | 통일 이전에 쓰인 링크. 옛 본문에 남아 있으므로 계속 받는다 |
| `[[아리]]` | **빨간 링크.** 접미사 `상대법`이 없으면 문서 이름이 아니다 |

마지막 줄이 중요하다. 챔피언 이름은 본문에 수없이 나오고 그 전부가 문서 링크인 것은
아니다. 접미사를 요구해야 `[[아리]]`가 실수로 링크가 되지 않는다.

**포지션별 상대법 차이는 어디로 가는가.** 섹션 축이 `내 챔피언`이고, 내 챔피언이
포지션을 이미 함축한다 — `제드로 상대할 때`는 미드 럭스를, `쓰레쉬로 상대할 때`는
서폿 럭스를 말한다. 그래서 포지션 섹션을 따로 두지 않는다. 두면 (포지션 × 내 챔피언)
행렬이 되고 채워지지 않는 칸이 대부분이 된다.

## `위키` 메뉴

`전적` 왼쪽, 즉 `상대법` 바로 다음에 놓는다. 이 사이트에서 위키는 곁다리가 아니라
본체이므로 `soon` 딱지가 붙은 메뉴들보다 앞선다.

```
상대법 · 위키 · 전적soon · 통계soon · 티어표soon · 강의soon
```

`/wiki` 아래에 다섯을 둔다.

| 화면 | 주소 | 하는 일 |
| --- | --- | --- |
| 문서 찾기 | `/wiki` | 관문 · 최근 변경 · 이름 검색 · 분류 나무. 이 메뉴의 첫 화면 — 아래 「첫 화면」 |
| 최근 바뀐 문서 | `/wiki/recent` | 시간순 피드. 매치업·일반 문서를 함께 |
| 아직 없는 문서 | `/wiki/wanted` | **구현됨.** 아직 안 쓰인 매치업 + `wiki_links`로 걸린 일반 문서 빨간 링크(4단계 일부) |
| 새 문서 제안 | `/wiki/new` | 제목을 정하고 첫 본문을 쓴다 |
| 문서 | `/wiki/<이름>` | 일반 문서 본문 |

`/wiki/recent`는 `listRecentChanges`를 공개용으로 한 번 더 쓰는 것이다. 관리자용
`/admin/wiki/recent`는 남긴다 — 그쪽은 "무검토 게시를 걸러 훑어보는" 감사 도구라
목적이 다르다.

### 첫 화면

`/wiki`는 이 잡지의 **목차 페이지**다. 포스터를 또 한 판 깔면 `상대법` 선택 화면과
구분이 안 된다. 목차는 선택 화면과 다르게 생겨야 한다.

```
┌────────────────────────────────────────────────────────────────────┐
│  뭘 찾아?                                     [ DOCS 128 / 7d 24 ] │
│                                                                    │
│ ┌──────────────────────── 8열 ────────────┬───────── 4열 ────────┐ │
│ │ 01 ─────────────────────────────  관문  │  ⌕ 문서 이름         │ │
│ │  ┌────────┐┌──────┐┌────┐               │ ──────────────────── │ │
│ │  │        ││      ││    │               │ 02 ─── 최근 바뀐 문서│ │
│ │  │ 라인전 ││ 운영 ││사전│               │  3시간  정글 동선    │ │
│ │  └────────┘└──────┘└────┘               │  5시간  룬 › 정밀    │ │
│ │    31        24      18                 │  어제   아리 상대법  │ │
│ │                                         │  …           전부 →  │ │
│ │  ↓ 고르면 이 아래로 목록이 펼쳐진다     │ ──────────────────── │ │
│ │    /wiki?분류=정글                      │ 03 ─── 손이 필요한 곳│ │
│ │                                         │   43   미분류 문서   │ │
│ │                                         │   17   아직 없는 문서│ │
│ └─────────────────────────────────────────┴──────────────────────┘ │
│ 04 ─────────────────────────────────────────────────────  분류 전부│
│  라인전 › 웨이브 · 갱 대비      운영 › 시야 · 오브젝트     분류 없음│
└────────────────────────────────────────────────────────────────────┘
```

**왼쪽은 인쇄된 것**(커버·분류·목차, 잘 안 변한다), **오른쪽은 덧칠한 메모**(시각·
숫자·방금 있었던 일, 매일 변한다). 블루프린트 1장의 "General은 인쇄된 본문이고
Me는 나중에 덧칠한 형광펜 메모다"가 화면 전체 규모로 한 번 더 나타난다.

상대법 화면이 `Aside 3.3 / Main 8.7`이므로 여기는 `8 / 4`로 둔다. 비율이 달라야 두
화면이 겹쳐 보이지 않는다. 모바일에서는 검색 → 관문 → 최근 → 일감 → 나무로 쌓는다.

### 생성 블루프린트

![깨남.COM 위키 목차 화면 블루프린트](./design/blueprints/wiki-index-v2.png)

- 문서가 충분히 쌓여 `라인전 / 운영 / 사전`이 **이번 호 표지**로 편성된 데스크톱 성장 상태다.
- `DOCS 128 / 7D 24`, 문서 수, 최근 변경 시각과 일감 수치는 조판을 확인하기 위한 예시이며 제품 데이터가 아니다.
- 관문 커버는 챔피언 대신 `라인전=웨이브·교환`, `운영=오브젝트·시야`, `사전=룬·아이템`을 직접 그린 인쇄 포스터로 제안한다.
- 표지는 `sort_order` 상위 셋만 `5 / 4 / 3`으로 조판하며 캐러셀로 돌리지 않는다. 나머지 관문과 하위 분류는 하단 나무에 글자로 모두 남는다.
- `정글`은 독립 관문 커버가 아니라 `라인전`과 `운영` 아래에 모두 나타나는 열린 하위 분류로 표현한다.
- 초기 관문 커버는 모두 `1536×1024` WebP다. 제목과 문서 수는 이미지에 굽지 않고 화면의 실제 텍스트로 겹친다.
  - 라인전: `/images/portal/lane-phase.webp`
  - 운영: `/images/portal/macro-play.webp`
  - 사전: `/images/portal/reference-guide.webp`
- 이후 표지 편성에 쓸 추가 관문 커버도 같은 규격으로 준비한다.
  - 밴픽: `/images/portal/draft-board.webp`
  - 한타: `/images/portal/teamfight-clash.webp`
- 구현 전 시각 방향 확인용이며, 승인되면 `DESIGN_BLUEPRINT.md`의 개발 시각 기준에 편입한다.

#### 다섯을 한 줄에 두지 않는다

`라인전` `운영` `사전` `최근 수정된 문서` `미분류 문서`를 나란한 커버 카드로 두면
두 가지가 깨진다.

**커버는 그릴 대상이 있는 것에만 붙는다.** `라인전`은 있고 `미분류 문서`는 없다.
억지로 붙이면 블루프린트 5장이 금지한 "의미 없는 장식"이 된다.

**저 둘은 내용이 이미지가 아니라 숫자다.** `미분류 43`에서 값을 가진 것은 43이고,
그 숫자가 **줄어드는 것을 보는 것**이 목적이다. 커버를 씌우면 숫자가 자막으로
밀린다. mono 큰 숫자 + 작은 라벨로 두면 `SelectionScreen`의 티켓·바코드 문법을
그대로 쓴다.

#### 조각별로

| 조각 | 정한 것 |
| --- | --- |
| 검색 | **실제 1순위 입구다.** 오른쪽 열 맨 위, 스크롤 없이 보인다. 결과는 드롭다운으로 덮지 않고 **오른쪽 열의 내용을 대체한다** — 종이 색인을 넘긴 것처럼. 자동완성 오버레이는 쓰지 않는다 |
| 관문 포스터 | 카테고리 포스터를 그대로 쓴다. `POSTER_WEIGHTS`, 라벨 튀어나오기, hover 가로 확장까지 이미 있다. 더하는 것은 라벨 아래 mono 한 줄 `문서 24`뿐이고, 이 한 줄이 두 화면을 구분한다 |
| 분류 펼치기 | 페이지를 떠나지 않는다. `?position=&category=`로 Contact Sheet를 펼치는 그 패턴을 `?분류=정글`로 쓴다. 펼쳐지는 것은 아이콘 격자가 아니라 **번호 + 제목 + 마지막 수정**의 얇은 가로 줄(블루프린트 6.3 Tip 문법)이다. 문서엔 아트가 없으므로 Contact Sheet를 그대로 쓸 수 없다. `분류:정글` 문서가 있으면 그 본문이 목록 위에 얹힌다 |
| 매치업 | **네 번째 포스터를 주지 않는다.** `상대법` 메뉴가 이미 그 입구다. 여기서는 나무의 첫 갈래로만 있고 검색·최근 변경에는 당연히 섞인다. 입구를 둘로 늘리지 않으면서 "목록도 최근 변경도 하나"를 지킨다. 포스터가 넷이 되면 `5/4/3` 조판이 깨지는 실무적 이유도 있다 |
| 최근 바뀐 문서 | 여덟 줄. `3시간 · 정글 동선 › 갱킹`. 시각은 mono, 문서명이 주인공, 섹션명은 Smoke. **이 위키가 살아 있다는 것을 증명하는 유일한 자리**라 짧아도 반드시 보인다 |
| 분류 나무 | 맨 아래, 글자만. 분류가 스무 개를 넘기 전에는 접지 않고 다 펼친다 |

#### 실제로 들어간 것

0단계에서 이 화면이 그대로 들어갔다. 다만 **블루프린트의 숫자는 전부 실제 값으로
바뀌었다.** 아직 셀 수 없는 것은 가짜 숫자를 두지 않고 비웠다 (블루프린트 6.5).

| 자리 | 지금 | 채워지는 때 |
| --- | --- | --- |
| `DOCS n / 7D n` | 실제 `wiki_docs` 행 수와 최근 7일 반영 편집 수 | — |
| `02 최근 바뀐 문서` | 실제 `listRecentChanges` 여덟 줄 | — |
| `아직 없는 문서` | 분류에 있으나 아직 안 쓰인 매치업 + `wiki_links`(2026-09-05, 마이그레이션 0008)로 걸린 일반 문서 빨간 링크를 합친 값 | — |
| `미분류 문서` | **자리를 비웠다.** `[[분류:…]]`가 아직 없어 셀 것이 없다 | 4단계 나머지(분류·관문) |
| 관문별 문서 수 | 0이므로 숫자 대신 `아직 없음` | 4단계 나머지(분류·관문) |
| 검색 | 매치업 문서 · 일반 문서 · 관문 이름 (1·2단계에서 일반 문서 이름을 더했다 — 있는 문서가 검색에 안 나오면 같은 문서가 다시 제안된다) | 5단계에 본문 |

`wiki_portals` 표는 아직 만들지 않았다. 관문 다섯은 `src/data/portals.ts`에 있고,
이는 `taxonomy.ts`가 운영 분류의 단일 원본인 것과 같은 자리다. 4단계에서 표와 관리
화면을 붙일 때 이 파일이 시드가 된다.

#### 켜는 순서

**일반 문서가 0개인 상태에서 포스터 세 장은 거짓말이다.** `라인전 0 · 운영 0 ·
사전 0`은 죽은 사이트로 보이고, 커버가 클수록 더 심하다.

| 언제 | 화면 |
| --- | --- |
| **0단계** | 관문 셋을 커버와 함께 켰다. 문서 수가 0이라 숫자 대신 `아직 없음`이 붙고, 오른쪽 열의 `아직 없는 문서`(194)가 실질적인 주인공이다 |
| 분류당 대여섯 개 | 그 관문만 켠다. 셋이 한꺼번일 필요 없다 — 하나면 `POSTER_WEIGHTS[1] = [8]`, 둘이면 `[7, 5]`가 이미 있다 |
| 셋 다 참 | 위 그림 |

포스터 수에 따라 12열을 다르게 나누는 규칙이 이미 있다는 것이 여기서 값을 한다.
**문서가 쌓이는 만큼 화면이 자란다.** 빈 커버를 먼저 걸고 채워지기를 기다리는 것보다 낫다.

#### 회전이 아니라 편성

관문은 운영하면서 계속 늘어도 된다. 다만 **캐러셀로 돌리지 않는다.**

**목차의 일은 전부 보여 주는 것이다.** 회전은 첫 화면 밖의 항목을 사실상 없는 것으로
만든다. 랜딩 배너라면 몰라도 여기는 찾으러 온 사람이 보는 목차이고, 잡지 목차는
돌아가지 않는다.

**이미 더 나은 규칙이 있다.** `POSTER_WEIGHTS`는 개수에 따라 12열을 다시 나눈다.
이 집의 문법은 "고정 슬롯에 넣고 남는 것을 감춘다"가 아니라 **"개수에 맞춰 조판을
다시 짠다"**이다.

**인터랙션이 충돌한다.** 포스터는 hover 시 가로로 확장되고 나머지가 축소된다. 그 위에
좌우 화살표를 얹으면 같은 가로축에서 두 동작이 싸우고, 터치에서는 스와이프까지 셋이 된다.

대신 `wiki_portals`는 늘리되 **표지에 걸리는 것은 `sort_order` 상위 셋뿐**이고,
나머지는 커버 없이 이름으로 나무 최상위에 선다.

```
01 ─────────────────  이번 호 표지
   [ 라인전 ]  [ 운영 ]  [ 사전 ]     ← 커버 3장. 조판은 [5,4,3]

04 ─────────────────  분류 전부
   밴픽 · 한타 · 정글 · 시야 · …      ← 커버 없이, 전부 여기 있다
```

**표지에 실리는 특집과 목차에 있는 전부는 다르다**는 잡지 문법 그대로다. 값이 셋 있다.

- **커버 제작 부담이 세 장으로 고정된다.** 관문이 여덟 개가 돼도 그림은 세 장이다.
- **운영자에게 손댈 이유가 생긴다.** "이번 패치엔 밴픽이 중요하니 표지를 밴픽으로."
  사이트가 살아 있다는 신호이고, 자동 회전보다 훨씬 강한 신호다.
- **아무것도 감추지 않는다.** 표지에 없는 관문도 같은 화면 아래에 이름으로 다 있다.

넷 이상을 한꺼번에 커버로 걸고 싶어지면 회전이 아니라 **두 줄 스프레드**다 —
윗줄 `[5,4,3]`, 아랫줄 `[7,5]`. 비대칭 두 줄은 잡지 펼침면 문법이라 이 집에 맞고,
모든 것이 한눈에 보인다.

### 아직 없는 문서 목록 — 구현됨 (2026-09-05, 마이그레이션 0008)

**이 목록이 이 확장에서 값이 크다.** 빈 위키의 문제는 "무엇을 쓸지 모르겠다"인데,
빨간 링크 목록은 이미 쓰인 문서들이 스스로 "이게 필요하다"고 말해 둔 것이다.
많이 걸린 이름부터 보여 주면 그게 곧 우선순위다.

실제 스키마는 표시용 이름 한 컬럼이 더 있다 — `target_key`(정규화된 이름)만으로는
목록에 "정글동선" 같은 붙은 꼴을 보여 주게 되어, 마지막으로 적힌 원문을 함께 저장한다.

```sql
CREATE TABLE wiki_links (
  source_doc   TEXT NOT NULL REFERENCES wiki_docs(id) ON DELETE CASCADE,
  source_key   TEXT,              -- 어느 섹션에서 걸었는지. NULL이면 본문
  target_key   TEXT NOT NULL,     -- 정규화한 대상 이름
  target_title TEXT NOT NULL,     -- 실제로 적힌 이름. 목록 표시용
  PRIMARY KEY (source_doc, source_key, target_key)
);
CREATE INDEX idx_links_target ON wiki_links (target_key);
```

**매치업 문서를 가리키는 링크는 담지 않는다.** `[[아리 상대법]]`은 챔피언 카탈로그에
있으면 문서가 비어 있어도 주소가 늘 열려 있어(`resolveWikiTitle`) "아직 없는 문서"가
아니다 — 그 목록은 이미 분류 기반으로 따로 있다(`getWikiIndexStats`). `wiki_links`에
남는 것은 전부 `unresolvedWikiTitles`가 걸러낸, 매치업으로 안 풀리는 이름뿐이다.

섹션을 저장할 때 그 섹션의 링크를 지우고 다시 넣는다(`wikiEditStore.ts`의
`linkStatements`, `submitEdit`·`approveEdit`·`revertDoc`·`proposeArticle`의 즉시게시
경로가 함께 쓴다). 같은 표가 **역링크**("이 문서를 가리키는 문서")도 공짜로 주지만,
그 화면은 아직 만들지 않았다.

`src/lib/wikiIndexStore.ts`의 `getWantedArticles()`/`countWantedArticles()`가 이미
게시된 문서를 뺀 채 `target_key`로 묶어 세고, `/wiki/wanted`와 `/wiki` 첫 화면의
"손이 필요한 곳" 숫자가 이 값을 매치업 목록과 합쳐서 보여 준다.

### 분류 — 구현됨 (2026-09-05)

나무위키처럼 **본문에 적는다.** `[[분류:룬]]`이다. 이미 `[[...]]` 문법이 있어
새 문법을 배울 것이 없고, 분류를 고치는 일이 본문을 고치는 일과 같은 규칙을 따른다.

`wikiMarkup.ts`의 `linkifyWikiLinks`가 `분류:` 접두 링크를 다른 위키링크와 다르게
다룬다 — 본문에는 그리지 않고(namuwiki처럼 태그로만), `ArticleScreen`이 본문 아래에
태그 줄로 따로 그린다. 소속 문서 조회는 `wikiStore.ts`의 `getCategoryView(name)`이
맡는다 — 관문(`src/data/portals.ts`)과 편집자가 만드는 하위분류가 같은 함수를 쓴다.
하위분류는 한 단계만 따라간다(관문 → 하위분류 → 그 문서). `/wiki` 첫 화면의 관문
카드 "펼치기" 패널(`WikiIndexScreen.tsx`)이 이 값을 실제로 보여주는 통로이고, "분류:
이름" 문서 자신의 페이지에도 소속 문서 목록이 자동으로 붙는다. 04 구역의 분류 나무도
관문 아래에 하위분류를 한 단(`TreeItem.children`)만큼 들여 그린다(2026-09-06) —
그 아래 손자 분류까지는 아직 안 간다.

분류는 **표의 행이 아니라 문서들이 가리키는 이름이다.** 아무도 만들지 않고, 누가
적으면 생기고, 적은 문서에서 전부 빠지면 사라진다. 나무위키가 그렇게 돈다.

#### 세 가지 행위

분류를 둘러싼 일은 셋이고, 서로 권한이 다르다.

| 행위 | 하는 법 | 누가 |
| --- | --- | --- |
| **문서에 분류를 단다** | 본문에 `[[분류:정글]]`을 적는다 | 아무나. 더하기만 하는 편집이라 **즉시 반영** |
| **분류 문서를 만든다** | `분류:정글` 문서를 쓴다. 상위 분류와 설명이 필요할 때만 | 아무나 제안, **운영자 승인** — 문서 생성이므로 위 규칙을 그대로 탄다 |
| **관문에 올린다** | `wiki_portals`에 한 줄 | **운영자만** |

둘째가 첫째의 전제가 아니다. `분류:정글` 문서가 없어도 `[[분류:정글]]`은 이미
돌아간다 — 목록도 나오고 `미분류 문서`에서도 빠진다. 분류 문서는 **나무에 자리를
잡을 때**(그 안에 `[[분류:운영]]`을 적어 상위를 정한다) 비로소 필요하다.

이 순서가 뒤집히면 안 된다. 분류를 달기 전에 나무의 자리를 먼저 정해야 하면
**아무도 분류를 안 단다.** 자리는 나중에 위에서 정리한다.

#### 관문은 분류가 아니다

`/wiki` 첫 화면의 커버 카드는 **관문**이고, 분류와 성질이 반대다.

| | 분류 | 관문 |
| --- | --- | --- |
| 개수 | 무한. 느는 게 정상 | 서넛. 늘면 실패 |
| 정하는 사람 | 편집자 | 운영자 |
| 딸린 것 | 없다. 이름뿐 | 커버 이미지 · 순서 · 설명 |
| 비어도 되나 | 된다 (`분류 없음`으로 간다) | 안 된다 (빈 커버는 못 건다) |

**커버 이미지가 필요하다는 사실 자체가 근거다.** 이미지를 붙여야 하는 집합은 열려
있을 수 없다. 편집자가 `[[분류:와딩]]`을 적었을 때 커버를 그릴 사람이 없다.

그래서 관문에 오른 분류가 **나무의 최상위**가 되고 그 아래는 완전히 열린다.
대문은 닫혀 있고 나무는 열려 있다.

```sql
-- 커버가 붙는 최상위 분류만 여기 있다. 운영자만 쓴다.
CREATE TABLE wiki_portals (
  key        TEXT PRIMARY KEY,   -- 분류 이름의 title_key. '라인전' | '운영' | '사전'
  label      TEXT NOT NULL,
  cover_path TEXT NOT NULL,
  blurb      TEXT,
  sort_order INTEGER NOT NULL    -- 상위 셋만 표지에 걸린다. 아래 "회전이 아니라 편성"
);
```

분류 자체는 새 저장소가 없다. `wiki_links`에 `target_key = '분류:정글'`로 이미 다
들어가 있다.

#### 관문은 한 축에서 고른다

포스터 세 장이 나란히 걸리면 독자는 **"이것들은 같은 종류다"**라고 읽는다. 축이
섞이면 문서가 어디 속하는지 예측할 수 없다 — `라인전`과 `정글`을 나란히 두면
`정글 동선`이 초반 동선이라 라인전인지, 카정·오브젝트라 정글인지 아무도 모른다.

분류는 여러 축을 겹쳐도 된다. 한 문서에 `[[분류:정글]]`과 `[[분류:운영]]`을 같이
단다. **커버가 붙는 최상위만 한 축이어야 한다.**

그리고 이 사이트에서 **포지션축은 쓸 수 없다.** `상대법` 메뉴가 이미 그 축을 통째로
갖고 있다. `정글`을 관문으로 올리는 순간 `서폿`(시야·로밍)도 올려야 하고, 결국
포지션 다섯 개를 위키 안에 다시 짓게 된다.

남는 것은 **시간축**이고, 마침 실력이 느는 순서와 같다.

| 관문 | 들어갈 문서 |
| --- | --- |
| **밴픽** | 조합, 카운터픽, 밴 우선순위, 픽 순서 |
| **라인전** | CS, 웨이브 관리, 견제, 갱 대비, 주도권, 정글 초반 동선 |
| **운영** | 시야, 오브젝트, 로밍, 스플릿, 텔포, 카정, 스노우볼 |
| **한타** | 포지셔닝, 진입 타이밍, 궁 순서, 어그로 |
| **사전** | 룬, 아이템, 용어, 시스템 수치 — 시간축 밖의 유일한 예외 |

처음 켜는 셋은 **`라인전` · `운영` · `사전`**이다. 초보가 실제로 검색하는 것이 저
셋이고, `밴픽`·`한타`는 문서가 몇 개 쌓인 뒤에 켠다.

`정글`이 관문에서 빠지지만 **버리는 것이 아니다.** `[[분류:정글]]`은 그대로 살아
`라인전`·`운영` 아래 하위 분류로 붙고, 나무를 세로로 관통한다.

#### 나무

매치업 문서는 분류를 적지 않는다. **포지션과 카테고리가 이미 분류다.** `/wiki`의
나무는 두 갈래를 함께 보여 준다.

```
상대법                          ← taxonomy.ts에서 자동
├── 미드 / 브루저 · 원딜 …
└── …
일반 문서
├── 라인전                      ← 관문. wiki_portals에 있다
│   └── 웨이브 · 갱 대비 · 정글   ← 편집자가 만든 하위 분류
├── 운영
│   └── 시야 · 오브젝트 · 정글    ← 같은 분류가 두 관문 아래 설 수 있다
├── 사전
├── 기타                        ← 상위를 못 잡은 분류. 운영자가 여기만 가끔 본다
└── 분류 없음                   ← 분류를 안 적은 문서도 반드시 보인다
```

## 새 문서 만들기

**문서 생성은 언제나 운영자 승인을 거친다.** 지운 것이 없어도 그렇다.

즉시 반영의 근거는 "더하기만 하는 편집은 잃을 것이 없다"였다. 문서 생성은 그 논리가
닿지 않는다 — **새 문서는 내용이 아니라 이름을 차지하기 때문이다.** 이름은 지운 것이
없다고 안전해지지 않고, 한 번 나쁜 이름이 생기면 목록·검색·분류를 계속 오염시킨다.
게다가 이름은 유일해서, 나중에 제대로 된 문서를 쓰려는 사람의 자리를 막는다.

```
        제목이 이미 있는 문서와 겹치는가?
                    │
    ┌──── 예 ───────┴────── 아니오 ─────┐
    ▼                                   ▼
  생성 불가                          검토 대기
 (그 문서로 보낸다)          운영자가 승인해야 문서가 생긴다
```

### 제목이 겹치면

겹침은 세 가지를 모두 본다. 하나라도 걸리면 만들지 않고 **그 문서로 데려간다** —
막다른 오류 화면보다 목적지가 낫다.

| 겹치는 대상 | 판정 방법 | 안내 |
| --- | --- | --- |
| 이미 있는 일반 문서 | `title_key`가 같다 | "이미 있는 문서입니다" + 그 문서로 |
| 매치업 문서 | `resolveWikiTitle(제목)`이 주소를 돌려준다 | `[[아리 상대법]]`은 이미 문서다 |
| 검토 중인 제안 | `title_key`가 같고 `doc_status = 'proposed'` | "누군가 먼저 제안했습니다" + 그 제안으로 |

셋째가 중요하다. **검토 중인 제안도 이름을 잡는다.** 그러지 않으면 승인을 기다리는
동안 같은 문서가 여럿 제안되고, 운영자가 그걸 다 읽어야 한다. 제안이 거절되면
이름이 풀린다.

이 판정도 다른 모든 판정과 같이 **저장 시점에 서버가** 한다. 제목 칸에서 미리 알려
주는 것은 편의일 뿐, 그 결과를 믿고 만들지 않는다.

### 승인되기까지

문서 행은 제안 시점에 `doc_status = 'proposed'`로 만들어진다. 이름을 잡아야 하고,
첫 본문이 평범한 `pending` 편집으로 그 문서에 달려야 하기 때문이다 — 그래야 검토
화면·문서 역사·`내 편집`이 전부 지금 그대로 돌아간다.

`proposed` 문서는 **어디에도 나오지 않는다.** 목록·분류·검색·`resolveWikiTitle`이
모두 `doc_status = 'published'`만 본다. 주소를 직접 아는 사람(제안자와 운영자)만
볼 수 있다.

운영자가 첫 편집을 승인하면 문서가 `published`가 된다.

거절하면 **`title_key`만 비우고 행은 남긴다** (`doc_status = 'rejected'`). 이름은 그
순간 풀려 다음 사람이 쓸 수 있다. 행까지 지우지 않는 것은 `wiki_edits`가 `ON DELETE
CASCADE`로 매달려 있어, 행을 지우면 그 제안 자체가 사라지고 제안자가 「내 편집」에서
거절 사유를 볼 수 없게 되기 때문이다 (FR-33). 이름 없는 껍데기는 어느 목록·검색·링크
해석에도 나오지 않는다.

**관리자가 낸 새 문서는 대기열을 거치지 않는다.** 자기 제안을 자기가 검토하는 줄은
뜻이 없고, 이 코드베이스는 이미 관리자 편집을 즉시 반영한다 (`submitEdit`).

### 진입점

빨간 링크를 누르면 그 이름으로 제안하는 화면이 열린다. 위키에서 빨간 링크는
**막다른 길이 아니라 초대**여야 한다.

```
[[룬]]  →  /wiki/룬  →  "아직 없는 문서입니다. 첫 번째로 써 보세요."  →  /wiki/new?title=룬
```

편집 화면은 `MergeEditScreen`을 그대로 쓴다. 왼쪽이 비어 있고 오른쪽이 전부 초록인
상태 — 지금 빈 섹션을 채울 때와 똑같은 화면이고, 위에 제목 칸이 하나 더 붙는다.
다만 안내는 다르다. 초록뿐이어도 **"운영자 승인 후 문서가 만들어집니다"**로 고정된다.

## 단계

각 단계가 끝날 때마다 쓸 수 있는 것이 하나씩 는다. 중간에 멈춰도 손해가 없게 나눴다.

| 단계 | 내용 | 스키마 |
| --- | --- | --- |
| **0. 메뉴와 목차** ✅ | `위키` 메뉴, `/wiki` 첫 화면(관문 포스터 포함), 분류 나무(매치업만), `/wiki/recent`·`/wiki/wanted` 공개 | 없음 |
| **1. 일반 문서 읽기** ✅ | `wiki_docs` 일반화, `/wiki/<이름>`, `resolveWikiTitle`에 갈래 추가 → 빨간 링크가 살아난다 | 열 추가 (0006) |
| **2. 새 문서 제안·승인** ✅ | `/wiki/new`, 겹침 판정, `proposed` → `published` | 없음 |
| **3. 일반 문서의 섹션** | 섹션 추가·이름 붙이기. `wiki_sections.title` | 열 추가 |
| **4. 링크와 분류** | `wiki_links`✅ · `아직 없는 문서`에 일반 문서 합치기✅ · `[[분류:…]]`✅ · 관문 펼치기 패널에 실제 목록✅ · 04 나무의 하위분류 중첩✅(2026-09-06) · 역링크 화면(문서→역링크 목록) · 관문 포스터 | 표 추가 (`wiki_links`✅ · `wiki_portals`) |
| **5. 검색** | 이름 검색. PRD "남은 결정"의 검색 범위를 여기서 닫는다 | 없음 |

0단계는 스키마를 건드리지 않고 오늘 바로 할 수 있다. 매치업 문서만으로도 "분류별로
정리된 문서 목록"과 "최근 바뀐 문서"는 이미 값이 있다.

3단계를 뒤로 미룬 것은 **일반 문서가 처음부터 여러 섹션을 필요로 하지 않기**
때문이다. 1·2단계의 일반 문서는 본문 하나로 시작하고, 섹션은 실제로 길어진 문서가
생겼을 때 붙인다. 스키마는 이미 받아들이고 있으므로 열 하나와 UI만 더하면 된다.

## 대가

**운영자 부담이 는다.** 문서 생성이 전부 검토를 거치므로, 대기열에 "섹션 고치기"와
"새 문서" 두 종류가 섞인다. 새 문서 검토는 내용보다 **이름을 판단하는 일**이라
성격이 다르니, 검토 화면에서 둘을 구분해 보여 줘야 한다.

**즉시 반영되는 면 자체는 넓어지지 않는다.** 문서 생성을 승인제로 둔 덕분에,
`WIKI_MODEL.md` "즉시 반영의 대가"가 경고한 면은 지금 크기 그대로다. 다만 일반
문서가 생기면 그 문서들의 섹션도 덧붙이기에 열리므로, 문서 수에 비례해 넓어진다.

**최근 변경 피드를 실제로 훑는 운영이 여전히 전제다.**

## 남은 결정

- **섹션 이름을 고치거나 지우는 일** — 3단계에서 정한다. 섹션 이름을 바꾸면 앵커가
  깨지고 그 앵커를 가리킨 링크가 죽는다. 매치업 문서에는 없던 문제다.
- **문서 이름 바꾸기** — 지금 제안에 없다. 이름이 곧 주소이자 링크의 대상이라,
  바꾸면 그 이름을 가리키던 링크가 전부 빨개진다. 넘겨주기(redirect) 없이는 열 수
  없는 기능이고, 넘겨주기는 표가 하나 더 필요하다.
- **문서 삭제** — 지금 제안에 없다. 되돌리기로 본문을 비울 수는 있으나 문서 행은
  남는다. 이름을 실제로 푸는 수단이 필요해지면 그때 정한다.
