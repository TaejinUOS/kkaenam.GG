# 위키 확장 — 일반 문서와 `위키` 메뉴 (제안)

> 상태: **제안** (2026-09-04). 아래 "결정된 것" 네 가지는 확정, 구현은 시작 전이다.
> `docs/WIKI_MODEL.md`의 후속이며, 그 문서의 결정을 뒤집지 않고 넓히기만 한다.
> 승인되면 `docs/PRD.md`에 FR을 추가하고, 이 문서가 그 부속 설계가 된다.

지금 위키에는 매치업 문서밖에 없다. 룬·정글 동선·용어 같은 **일반 문서**를 들이고,
그 전부를 한자리에서 찾을 수 있는 `위키` 메뉴를 만든다.

## 결정된 것

| 물음 | 결정 |
| --- | --- |
| 새 문서 생성 | **제목이 겹치면 생성 불가.** 그 밖에는 전부 보류되고 운영자가 승인해야 만들어진다 |
| 일반 문서의 섹션 | **상대법 문서와 같다.** 본문 + 이름 붙은 섹션들, 편집 단위도 그대로 |
| 매치업 문서 | `위키` 메뉴에 함께 담는다. 목록도 최근 변경도 하나다 |
| 주소 | 한글을 쓴다. `/wiki/정글 동선` |

## 이미 준비된 것

새로 지어야 할 것이 생각보다 적다. 확장을 미리 염두에 두고 지은 자리가 남아 있다.

| 있는 것 | 확장에 쓰이는 방식 |
| --- | --- |
| `resolveWikiTitle` | "일반 문서 저장소가 생기면 갈래를 하나 더 둔다"고 주석에 적어 둔 그 자리 |
| `wiki_edits` · `wiki_sections` | 전부 `doc_id` 기준이다. **매치업에 매여 있지 않다** |
| 편집·검토·역사·되돌리기 | 섹션 단위로 돌아가므로 문서 종류를 묻지 않는다 |
| `listRecentChanges` | 이미 있다. 지금은 관리자 전용일 뿐이다 |
| `MergeEditScreen` | 빈 본문에서 시작하면 그대로 "새 문서 쓰기"다 |
| `WikiDocument` | 섹션 목록을 받아 그린다. 섹션이 어디서 왔는지 묻지 않는다 |

매치업에 매여 있는 것은 **주소를 다루는 얇은 층**뿐이다. `submitEdit`이
`(포지션, 챔피언)`으로 `doc_id`를 만들고, 조회 함수들이 그 두 열을 함께 SELECT해
화면이 `/matchup/...` 주소를 짓는다. 이 층만 "문서를 가리키는 법"으로 한 단계
올리면 나머지는 그대로 쓴다.

## 한 이름 공간에 두 종류

문서를 두 저장소로 쪼개지 않는다. 쪼개면 편집·검토·역사·최근 변경이 전부 두 벌이
되고, "최근 바뀐 문서"를 보려면 두 목록을 번갈아 봐야 한다.

```
wiki_docs
├── kind = 'matchup'   →  (position_slug, champion_slug)로 식별.  /matchup/mid/ahri
└── kind = 'article'   →  title_key로 식별.                      /wiki/룬
```

### 섹션은 상대법 문서와 같다

일반 문서도 **본문 하나 + 이름 붙은 섹션 여럿**이다. 매치업 문서에서 `공통 상대법` +
`제드로 상대할 때` `야스오로 상대할 때`인 것이, 룬 문서에서는 `본문` +
`정밀` `지배` `마법`이 된다. 목차 하나로 이어지고 번호가 문서 전체를 관통하는 것도,
섹션이 곧 편집 단위이자 즉시반영·검토 판정 단위인 것도 그대로다.

**다른 것은 섹션 이름이 어디서 오는가뿐이다.**

| | 매치업 문서 | 일반 문서 |
| --- | --- | --- |
| 섹션 이름 | 챔피언 카탈로그에서 고른다 (`MeCombobox`) | 편집자가 직접 적는다 |
| 이름 저장 | 안 한다 — 슬러그로 카탈로그를 되찾는다 | `wiki_sections`에 함께 저장해야 한다 |
| 앵커 | `me-<챔피언 슬러그>` | `s-<섹션 키>` |

그래서 `wiki_sections.me_slug`는 이제 **섹션 키**다. 매치업에서는 챔피언 슬러그이고
일반 문서에서는 섹션 이름을 정규화한 값이다. 열 이름은 바꾸지 않는다 —
`wiki_edits.me_slug`가 짝을 이루고 있어 함께 바꾸면 손댈 곳이 넓어진다. 주석으로 뜻을
넓히는 편이 싸다.

### 스키마 변경

```sql
-- wiki_docs에 더한다.
kind        TEXT NOT NULL DEFAULT 'matchup',   -- 'matchup' | 'article'
title       TEXT,                              -- 일반 문서의 표시 이름. 예: '정글 동선'
title_key   TEXT,                              -- 정규화한 이름. 주소이자 유일성의 근거
-- 'published' | 'proposed'. 승인 전 문서는 목록·링크·검색 어디에도 나오지 않는다.
doc_status  TEXT NOT NULL DEFAULT 'published',

-- position_slug / champion_slug는 NOT NULL을 푼다.
CREATE UNIQUE INDEX idx_docs_matchup ON wiki_docs (position_slug, champion_slug)
  WHERE kind = 'matchup';
-- 승인 전 제안도 같은 이름을 잡는다. 아래 "제목이 겹치면" 참고.
CREATE UNIQUE INDEX idx_docs_article ON wiki_docs (title_key)
  WHERE kind = 'article';

-- wiki_sections에 더한다. 일반 문서의 섹션 이름.
-- 매치업 문서는 NULL이다 — 이름을 챔피언 카탈로그가 갖고 있다.
title       TEXT;
```

**SQLite는 NOT NULL을 ALTER로 풀 수 없다.** 새 표를 만들어 복사하고 바꿔 다는
12단계 절차를 써야 한다. 마이그레이션 파일 하나로 끝나지만, 되돌릴 수 없는 작업이라
`docs/DEPLOY.md`의 "스키마를 먼저, 코드를 나중에" 순서를 반드시 지킨다.

`doc_id`는 지금 `doc-<포지션>-<챔피언>`이다. **기존 값을 건드리지 않는다** —
`wiki_edits`·`wiki_sections`가 전부 이 값을 참조하고 있다. 일반 문서는
`doc-a-<title_key>`로 짓는다.

### 이름이 곧 주소다

`[[정글 동선]]`이라고 쓰면 그 이름으로 문서를 찾는다. 이름과 주소가 따로 놀면
편집자가 둘을 함께 관리해야 하는데, 그건 사람이 지킬 규칙이 아니다.

`title`은 보여줄 이름 그대로 두고, `title_key`는 `wikiLink.ts`의 `normalize()`와
같은 규칙(소문자·공백 제거)으로 만든다. 그래야 `[[정글 동선]]`과 `[[정글동선]]`이
같은 문서에 닿는다. 주소는 `/wiki/정글 동선`을 URL 인코딩한 것이다.

## `위키` 메뉴

`전적` 왼쪽, 즉 `상대법` 바로 다음에 놓는다. 이 사이트에서 위키는 곁다리가 아니라
본체이므로 `soon` 딱지가 붙은 메뉴들보다 앞선다.

```
상대법 · 위키 · 전적soon · 통계soon · 티어표soon · 강의soon
```

`/wiki` 아래에 다섯을 둔다.

| 화면 | 주소 | 하는 일 |
| --- | --- | --- |
| 문서 찾기 | `/wiki` | 분류 나무 + 이름 검색. 이 메뉴의 첫 화면 |
| 최근 바뀐 문서 | `/wiki/recent` | 시간순 피드. 매치업·일반 문서를 함께 |
| 아직 없는 문서 | `/wiki/wanted` | 빨간 링크 모음. **무엇을 써야 하는지 알려 주는 목록** |
| 새 문서 제안 | `/wiki/new` | 제목을 정하고 첫 본문을 쓴다 |
| 문서 | `/wiki/<이름>` | 일반 문서 본문 |

`/wiki/recent`는 `listRecentChanges`를 공개용으로 한 번 더 쓰는 것이다. 관리자용
`/admin/wiki/recent`는 남긴다 — 그쪽은 "무검토 게시를 걸러 훑어보는" 감사 도구라
목적이 다르다.

### 아직 없는 문서 목록

**이 목록이 이 확장에서 값이 크다.** 빈 위키의 문제는 "무엇을 쓸지 모르겠다"인데,
빨간 링크 목록은 이미 쓰인 문서들이 스스로 "이게 필요하다"고 말해 둔 것이다.
많이 걸린 이름부터 보여 주면 그게 곧 우선순위다.

이걸 만들려면 링크를 표로 갖고 있어야 한다.

```sql
CREATE TABLE wiki_links (
  source_doc  TEXT NOT NULL REFERENCES wiki_docs(id) ON DELETE CASCADE,
  source_key  TEXT,              -- 어느 섹션에서 걸었는지. NULL이면 본문
  target_key  TEXT NOT NULL,     -- 정규화한 대상 이름
  PRIMARY KEY (source_doc, source_key, target_key)
);
CREATE INDEX idx_links_target ON wiki_links (target_key);
```

섹션을 저장할 때 그 섹션의 링크를 지우고 다시 넣는다. 같은 표가 **역링크**
("이 문서를 가리키는 문서")도 공짜로 준다.

### 분류

나무위키처럼 **본문에 적는다.** `[[분류:룬]]`이다. 이미 `[[...]]` 문법이 있어
새 문법을 배울 것이 없고, 분류를 고치는 일이 본문을 고치는 일과 같은 규칙을 따른다.

매치업 문서는 분류를 적지 않는다. **포지션과 카테고리가 이미 분류다.** `/wiki`의
나무는 두 갈래를 함께 보여 준다.

```
상대법                          ← taxonomy.ts에서 자동
├── 미드 / 브루저 · 원딜 …
└── …
일반 문서                       ← [[분류:…]]에서
├── 룬
├── 정글 동선
└── 분류 없음                   ← 분류를 안 적은 문서도 반드시 보인다
```

## 새 문서 만들기

**문서 생성은 언제나 운영자 승인을 거친다.** 지운 것이 없어도 그렇다.

즉시 반영의 근거는 "더하기만 하는 편집은 잃을 것이 없다"였다. 문서 생성은 그 논리가
닿지 않는다 — **새 문서는 내용이 아니라 이름을 차지하기 때문이다.** 이름은 지운 것이
없다고 안전해지지 않고, 한 번 나쁜 이름이 생기면 목록·검색·분류를 계속 오염시킨다.
게다가 이름은 유일해서, 나중에 제대로 된 문서를 쓰려는 사람의 자리를 막는다.

```
        제목이 이미 있는 문서와 겹치는가?
                    │
    ┌──── 예 ───────┴────── 아니오 ─────┐
    ▼                                   ▼
  생성 불가                          검토 대기
 (그 문서로 보낸다)          운영자가 승인해야 문서가 생긴다
```

### 제목이 겹치면

겹침은 세 가지를 모두 본다. 하나라도 걸리면 만들지 않고 **그 문서로 데려간다** —
막다른 오류 화면보다 목적지가 낫다.

| 겹치는 대상 | 판정 방법 | 안내 |
| --- | --- | --- |
| 이미 있는 일반 문서 | `title_key`가 같다 | "이미 있는 문서입니다" + 그 문서로 |
| 매치업 문서 | `resolveWikiTitle(제목)`이 주소를 돌려준다 | `[[미드/아리]]`는 이미 문서다 |
| 검토 중인 제안 | `title_key`가 같고 `doc_status = 'proposed'` | "누군가 먼저 제안했습니다" + 그 제안으로 |

셋째가 중요하다. **검토 중인 제안도 이름을 잡는다.** 그러지 않으면 승인을 기다리는
동안 같은 문서가 여럿 제안되고, 운영자가 그걸 다 읽어야 한다. 제안이 거절되면
이름이 풀린다.

이 판정도 다른 모든 판정과 같이 **저장 시점에 서버가** 한다. 제목 칸에서 미리 알려
주는 것은 편의일 뿐, 그 결과를 믿고 만들지 않는다.

### 승인되기까지

문서 행은 제안 시점에 `doc_status = 'proposed'`로 만들어진다. 이름을 잡아야 하고,
첫 본문이 평범한 `pending` 편집으로 그 문서에 달려야 하기 때문이다 — 그래야 검토
화면·문서 역사·`내 편집`이 전부 지금 그대로 돌아간다.

`proposed` 문서는 **어디에도 나오지 않는다.** 목록·분류·검색·`resolveWikiTitle`이
모두 `doc_status = 'published'`만 본다. 주소를 직접 아는 사람(제안자와 운영자)만
볼 수 있다.

운영자가 첫 편집을 승인하면 문서가 `published`가 된다. 거절하면 문서 행을 지운다 —
이름을 풀어 줘야 다음 사람이 쓸 수 있다.

### 진입점

빨간 링크를 누르면 그 이름으로 제안하는 화면이 열린다. 위키에서 빨간 링크는
**막다른 길이 아니라 초대**여야 한다.

```
[[룬]]  →  /wiki/룬  →  "아직 없는 문서입니다. 첫 번째로 써 보세요."  →  /wiki/new?title=룬
```

편집 화면은 `MergeEditScreen`을 그대로 쓴다. 왼쪽이 비어 있고 오른쪽이 전부 초록인
상태 — 지금 빈 섹션을 채울 때와 똑같은 화면이고, 위에 제목 칸이 하나 더 붙는다.
다만 안내는 다르다. 초록뿐이어도 **"운영자 승인 후 문서가 만들어집니다"**로 고정된다.

## 단계

각 단계가 끝날 때마다 쓸 수 있는 것이 하나씩 는다. 중간에 멈춰도 손해가 없게 나눴다.

| 단계 | 내용 | 스키마 |
| --- | --- | --- |
| **0. 메뉴와 목차** | `위키` 메뉴, `/wiki` 분류 나무(매치업만), `/wiki/recent` 공개 | 없음 |
| **1. 일반 문서 읽기** | `wiki_docs` 일반화, `/wiki/<이름>`, `resolveWikiTitle`에 갈래 추가 → 빨간 링크가 살아난다 | 표 재작성 |
| **2. 새 문서 제안·승인** | `/wiki/new`, 겹침 판정, `proposed` → `published` | 없음 |
| **3. 일반 문서의 섹션** | 섹션 추가·이름 붙이기. `wiki_sections.title` | 열 추가 |
| **4. 링크와 분류** | `wiki_links`, 역링크, `아직 없는 문서`, `[[분류:…]]` | 표 추가 |
| **5. 검색** | 이름 검색. PRD "남은 결정"의 검색 범위를 여기서 닫는다 | 없음 |

0단계는 스키마를 건드리지 않고 오늘 바로 할 수 있다. 매치업 문서만으로도 "분류별로
정리된 문서 목록"과 "최근 바뀐 문서"는 이미 값이 있다.

3단계를 뒤로 미룬 것은 **일반 문서가 처음부터 여러 섹션을 필요로 하지 않기**
때문이다. 1·2단계의 일반 문서는 본문 하나로 시작하고, 섹션은 실제로 길어진 문서가
생겼을 때 붙인다. 스키마는 이미 받아들이고 있으므로 열 하나와 UI만 더하면 된다.

## 손대야 하는 곳

주소를 다루는 얇은 층만 올린다. 아래 목록이 그 전부다.

| 파일 | 무엇을 |
| --- | --- |
| `src/lib/wikiEditStore.ts` | `submitEdit`·`revertDoc`·`listDocHistory`가 `(포지션, 챔피언)` 대신 문서 참조를 받는다. 문서 생성·승인·거절이 더해진다 |
| `src/lib/actions/wikiEditActions.ts` | 같은 이유. `revalidatePath` 대상도 문서 종류에 따라 갈린다 |
| `src/lib/wikiLink.ts` | `resolveWikiTitle`에 일반 문서 갈래 추가. 주석이 예고한 그 변경 |
| `src/lib/wikiStore.ts` | `getWikiView`가 문서 참조로 읽는다. `doc_status` 거르기 |
| `src/components/matchup/MergeEditScreen.tsx` | 매치업 전용 props를 문서 참조로. 제목 칸을 옵션으로 |
| `src/app/admin/wiki/review/**` | 문서 생성 제안을 검토 대상에 포함 |
| `src/components/SiteHeader.tsx` | `NAV`에 한 줄 |
| `src/app/wiki/**` | 새 화면들 |

`WikiDocument` · `MarkdownBody` · `DiffText` · `HighlightedEditor` · `wikiDiff`는
**손대지 않는다.** 문서 종류를 모르는 채로 이미 옳다.

## 대가

**운영자 부담이 는다.** 문서 생성이 전부 검토를 거치므로, 대기열에 "섹션 고치기"와
"새 문서" 두 종류가 섞인다. 새 문서 검토는 내용보다 **이름을 판단하는 일**이라
성격이 다르니, 검토 화면에서 둘을 구분해 보여 줘야 한다.

**즉시 반영되는 면 자체는 넓어지지 않는다.** 문서 생성을 승인제로 둔 덕분에,
`WIKI_MODEL.md` "즉시 반영의 대가"가 경고한 면은 지금 크기 그대로다. 다만 일반
문서가 생기면 그 문서들의 섹션도 덧붙이기에 열리므로, 문서 수에 비례해 넓어진다.

**최근 변경 피드를 실제로 훑는 운영이 여전히 전제다.**

## 남은 결정

- **섹션 이름을 고치거나 지우는 일** — 3단계에서 정한다. 섹션 이름을 바꾸면 앵커가
  깨지고 그 앵커를 가리킨 링크가 죽는다. 매치업 문서에는 없던 문제다.
- **문서 이름 바꾸기** — 지금 제안에 없다. 이름이 곧 주소이자 링크의 대상이라,
  바꾸면 그 이름을 가리키던 링크가 전부 빨개진다. 넘겨주기(redirect) 없이는 열 수
  없는 기능이고, 넘겨주기는 표가 하나 더 필요하다.
- **문서 삭제** — 지금 제안에 없다. 되돌리기로 본문을 비울 수는 있으나 문서 행은
  남는다. 이름을 실제로 푸는 수단이 필요해지면 그때 정한다.
