## 2. 임시 구현 — 실서비스 전 반드시 교체

### 2.1 로그인과 편집이 아직 없다 ← 가장 중요

**지금 상태.** 상대법은 Cloudflare D1에 있고 문서 열람은 동작한다. 그러나 **로그인과
편집이 없다.** 옛 Tip 게시판(작성·수정·삭제·좋아요, `localStorage` 기반)은 위키 전환
2단계에서 걷어냈고, 위키 편집 화면은 4단계에 붙는다.

즉 현재 사이트는 **읽기 전용**이다. 시드 이관분 외에는 내용이 늘지 않는다.

**남은 단계.** 설계는 [`docs/WIKI_MODEL.md`](./WIKI_MODEL.md)에 있다.

| 단계 | 내용 | 관련 요구사항 |
| --- | --- | --- |
| 3 | 구글·카카오 소셜 로그인 | FR-22 |
| 4 | 편집 제안, 검토, 문서 역사, 되돌리기, 최근 변경, 제출 제한 | FR-24 ~ 33 |

**3단계의 알려진 위험.** 로그인 라이브러리(Auth.js)가 Cloudflare Workers 런타임에서
동작하는지는 실제로 붙여 봐야 안다. Workers는 Node가 아니라 라이브러리가 그대로 돌지
않는 경우가 있다. 작은 검증을 먼저 하고, 안 되면 직접 구현으로 방향을 튼다.

**3단계에 사람 손이 필요하다.** Google Cloud Console과 카카오 개발자 사이트에서 앱 등록,
도메인 등록, 키 발급을 해야 한다. 코드만으로 끝나지 않는다.

> 4단계에서 **즉시 반영 판정은 반드시 서버에서** 해야 한다. 빈 섹션은 바로 반영되고 이미
> 쓰인 섹션은 검토를 거치는데, 이 판정을 클라이언트가 주장하게 두면 검토를 우회할 수 있다.
> 섹션을 비우는 편집도 언제나 검토 대기다. PRD 5.4.1과 10장을 따른다.

> 즉시 반영 경로를 유지하려면 **최근 변경 화면, 한 번에 되돌리기, 제출 수 제한** 셋이
> 함께 있어야 한다. 하나라도 빠지면 도배에 무방비다 (PRD 10 보안 및 운영).

### 2.2 영상 탭

`영상` 탭은 **빈 상태 안내만** 보여 준다. 가짜 썸네일이나 임시 영상은 넣지 않았다.
PRD 3.2가 가짜 데이터를 금지하고, 영상의 출처·임베드 허용 범위·등록 검수 주체가
PRD 15 미결정 8번으로 남아 있기 때문이다.

블루프린트 6.4의 2열 골격은 자리만 잡아 두었으니, 출처가 정해지면
[`src/components/matchup/VideoPanel.tsx`](../src/components/matchup/VideoPanel.tsx)에
목록을 채우면 된다. 데이터 형태는 PRD 8장 "영상" 항목을 따른다.

### 2.3 섹션 길이 제한과 본문 형식이 미정이다

편집 화면이 아직 없어 길이 제한을 강제하는 곳도 없다. 4단계에서 정해야 하며,
PRD 15 미결정 5·6·7번에 걸려 있다.

| 항목 | 상태 |
| --- | --- |
| 섹션 내용 최소·최대 길이 | 미정 (미결정 5번) |
| 편집 요약 필수 여부와 최대 길이 | 미정 (미결정 6번) |
| 계정당 시간당 제출 수 상한 | 미정 (미결정 7번) — FR-32가 요구하므로 4단계 전에 정해야 한다 |

**마크다운 지원 여부도 미정이다.** 현재 문서 본문은 평문으로 저장하고 화면에서는 빈 줄
기준으로 문단만 나눈다 ([`WikiPanel.tsx`](../src/components/matchup/WikiPanel.tsx)의
`Body`). 시드 이관 시 옛 Tip 제목을 본문 앞 줄로 넣었는데, 마크다운을 도입하면 그 줄을
제목 문법으로 바꾸는 재이관이 필요하다.

## 4. 관리자 챔피언 분류 ← 범위에 다시 들어옴

### 4.1 결정

v0.7에서 걷어냈던 **관리자 챔피언 분류를 범위에 되돌린다** (2026-09-02 결정).
PRD v0.8에 5.6절과 FR-34~43으로 복원했다. 고아로 남아 있던 용어 6개
(`챔피언 운영 상태`, `분류 검토 상태`, `데이터 소스 상태`, `분류 노출 상태`,
`분류 보관`, `미분류`)와 목표 6 "배포 없이 갱신", 대상 사용자의 "운영 사용자"가
다시 살아 있는 요구사항이 되었다.

미뤄 두었던 대안(목표에서 "배포 없이"를 빼는 안)은 채택하지 않았다.

### 4.2 이 결정이 코드에 요구하는 것

**분류가 코드에서 데이터베이스로 옮겨간다.** 이것이 이 결정의 실질이며, 지금 구조에서
가장 큰 변경이다.

| 지금 | 바뀐 뒤 |
| --- | --- |
| [`src/data/taxonomy.ts`](../src/data/taxonomy.ts)가 분류의 단일 원본 | D1이 단일 원본. `taxonomy.ts`는 초기 이관 자료로만 남는다 |
| 명단을 고치려면 파일 수정 + 배포 | 관리자 화면에서 즉시 반영 |
| `champions.ts`가 **모듈 로드 시점에** 이름을 카탈로그와 대조하고 틀리면 throw | 쓰기 시점 검증으로 옮긴다. 카탈로그에 없는 챔피언은 배정 자체가 막힌다 (FR-42) |
| 챔피언이 카탈로그에서 사라지면 앱이 뜨지 않는다 | `소스 누락 검토 필요`로 표시만 하고 서비스는 계속 뜬다 (FR-41) |

### 4.3 알려진 위험 — 220ms 전환

[`src/data/selection.ts`](../src/data/selection.ts)는 분류 전체(약 23KB, 배정 185건)를
직렬화해 첫 응답에 실어 보낸다. 포지션·카테고리 전환마다 서버를 왕복하면
`DESIGN_BLUEPRINT.md`가 규정한 **220ms 전환을 지킬 수 없기 때문이다.**

분류를 D1로 옮기면 이 데이터를 매 요청 조회해야 한다. 그대로 하면 첫 응답이 느려진다.

**이전 전후로 전환 시간을 실측해 비교할 것.** 느려지면 분류 조회 결과를 캐시한다.
분류는 관리자가 가끔 바꾸는 데이터라 캐시 적중률이 높고, 무효화 시점도 명확하다
(관리자가 저장할 때).

### 4.4 남은 작업

| 작업 | 관련 요구사항 |
| --- | --- |
| 분류·챔피언 상태 표를 D1에 만든다 | 8장 "포지션별 챔피언 분류", "분류 변경 이력" |
| `taxonomy.ts` → D1 이관 스크립트 | 시드 이관(`scripts/seed-wiki.ts`)과 같은 방식 |
| `selection.ts`와 `champions.ts`를 D1 조회로 바꾸고 전환 시간 실측 | 4.3 |
| 관리자 역할 판정과 접근 제어 | FR-34 |
| 분류 관리 화면과 API | FR-35~42 |
| 분류 변경 이력 | FR-43 (P1) |

**로그인(3단계)이 선행 조건이다.** 관리자 역할을 판정할 수단이 없으면 FR-34를 만들 수 없다.
위키 편집(4단계)과는 독립이므로 순서는 3단계 뒤 어디든 놓을 수 있다.

### 4.5 아직 정해지지 않은 것

**어떤 기준으로 배정할지는 여전히 미정이다** (PRD 15 미결정 1번). 관리자 화면은 갱신
*수단*을 제공할 뿐, 아리를 `mage`에 둘지 판단해 주지 않는다. 현재 분류는
`taxonomy.ts`에 담긴 초기 운영 분류이며 그 근거는 `archive/plan1.txt`의 미드 세 카테고리뿐이다.

## 5. 운영하면서 알아야 할 것

### 5.1 `dev`와 `build`를 동시에 돌리지 말 것

둘 다 같은 `.next` 디렉터리를 쓴다. dev 서버를 켠 채 `npm run build`를 돌리면 dev 서버가
빈 페이지나 500을 뱉기 시작한다. 이 경우 **코드 문제가 아니다.** dev 서버를 끄고
`.next`를 지운 뒤 다시 켜면 된다.

```bash
rm -rf .next && npm run dev
```

### 5.2 패치 갱신

```bash
DDRAGON_PATCH=16.18.1 npm run data:sync   # 챔피언·스킬 다시 내려받기
npx tsx scripts/check-taxonomy.ts          # 이름이 깨지지 않았는지 점검
```

패치 버전과 갱신 시각은 `src/data/generated/champions.json`에 저장되고 사이트 하단에
표시된다. 신규 챔피언이 나오면 `taxonomy.ts`에 직접 배정해야 목록에 나온다.

### 5.3 챔피언 분류 갱신

> **이 절은 관리자 화면이 생기면 바뀐다.** 분류는 D1로 옮겨가고 `taxonomy.ts`는 초기
> 이관 자료로만 남는다 (4장). 아래는 그때까지의 방식이다.

포지션·카테고리와 챔피언 명단은 [`src/data/taxonomy.ts`](../src/data/taxonomy.ts)
**한 곳에서만** 관리한다. 화면 코드에 챔피언을 개별로 고정하지 않는다 (PRD 5.1).

- 이름은 Data Dragon `ko_KR` 표기와 **정확히** 일치해야 한다. `리 신`, `트위스티드 페이트`,
  `아우렐리온 솔`, `문도 박사`처럼 띄어쓰기가 있는 이름을 조심할 것.
- 틀리면 앱이 뜰 때 오류로 잡히고, `check-taxonomy.ts`가 어떤 이름인지 알려 준다.
- 한 챔피언이 여러 포지션에 속할 수 있지만 **같은 포지션 안에서는 카테고리 하나뿐**이다.
  점검 스크립트가 중복도 잡는다.
- 분류에 없는 조합(`/matchup/mid/leesin` 같은)은 404가 된다. 의도된 동작이다 (FR-07).

공개 배포 전에 Riot 정책을 다시 검토할 것.

### 5.5 모바일 헤더 메뉴가 가로로 넘친다

360px에서 메뉴 다섯 개(`상대법 / 전적 / 통계 / 티어표 / 강의`)의 폭이 254px인데
로고와 마이페이지 아바타를 빼면 172px만 남는다. 세 개 반만 보이고 나머지는 가로 스크롤이다.
오른쪽 끝을 흐리게 처리해 더 있다는 것은 알 수 있게 했다.

글자와 여백을 최대로 줄여도 82px이 모자라므로, 제대로 풀려면 둘 중 하나가 필요하다.

1. 모바일에서 햄버거 메뉴로 전환한다 (블루프린트에 모바일 헤더 규격이 없어 새로 정해야 함)
2. 모바일 헤더에서는 `강의`처럼 우선순위가 낮은 항목을 빼고 마이페이지 안으로 옮긴다

지금은 스크롤로 모든 메뉴에 닿을 수 있어 기능상 막힌 곳은 없다.

### 5.6 브라우저 저장소 키 — 더 이상 쓰지 않는다

옛 Tip 게시판이 쓰던 키다. 위키 전환 2단계에서 `tipStore.ts`와 함께 걷어냈으므로 앱은
이제 아무것도 읽고 쓰지 않는다. **이전에 사이트를 방문한 브라우저에는 값이 남아 있다.**

```
kkaenam.tips.v1     내가 쓴 Tip
kkaenam.votes.v1    좋아요 · 싫어요
kkaenam.user.v1     로컬 데모 계정
```

남은 값은 동작에 영향을 주지 않지만, 정리하려면 개발자 도구에서 삭제하면 된다.
3단계에서 로그인을 붙일 때 세션 키가 새로 생기며 이 키들과는 무관하다.

### 5.7 D1 데이터베이스

상대법 저장소는 Cloudflare D1 `kkaenam-gg` (APAC)이다.

```bash
npx wrangler d1 migrations apply kkaenam-gg --local    # 로컬 스키마
npx wrangler d1 migrations apply kkaenam-gg --remote   # 운영 스키마
npx wrangler d1 execute kkaenam-gg --remote --command "SELECT COUNT(*) FROM wiki_docs;"
```

**생성된 시드 SQL을 `migrations/`에 두지 말 것.** wrangler가 그 디렉터리의 `.sql`을 전부
마이그레이션으로 취급해 나중에 `migrations apply`를 돌릴 때 시드가 다시 실행된다.
`seeds/`에 두는 이유가 이것이다.
